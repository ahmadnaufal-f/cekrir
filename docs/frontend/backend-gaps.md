# Frontend/backend and hardware alignment gaps

This is a handoff of dependencies that prevent the frontend from claiming live integration. It follows the [Frontend Codex Handoff](https://app.notion.com/p/4193556fda92818e9719e95fbac4b667), [Frontend API and Mock Contract](https://app.notion.com/p/4193556fda92812ba7bef45b4699ec2f), [Android Push Notifications and Delivery Navigation](https://app.notion.com/p/4193556fda9281af98bfc3a7b7a32c1f), and [Frontend Device and Member Setup](https://app.notion.com/p/4193556fda92812f958dfde3f3644d61). Those documents label endpoint and DTO proposals as drafts; this page does not make them backend decisions.

The frontend work leaves `apps/backend` and `apps/esp32` unchanged. Proposed `/v1` routes must be compared with the current backend contract and adapted at the frontend service boundary. The API brief's 2026-11-15 source review reports legacy `/api/v1/shipments`, `/api/v1/notifications`, and detection routes in [routes.py](../../apps/backend/src/cekrir/api/routes.py); it does not verify household auth, delivery detail/photo, devices, members, or push-installation operations from the draft.

Owners: the teammate owns backend, scanner firmware, and hardware integration; the project initiator owns frontend and BARDI validation. Contract and new technology selections need their agreement.

The contextual setup UI added on 2026-11-16 does not verify device connectivity. Agree how a one-time ESP32 registration credential maps to firmware authentication: the existing shared ingestion key is not yet an agreed per-device credential. Inline guidance keeps this integration pending and links to the reviewed firmware scaffold; BARDI guide references remain unavailable until validated. Guide visibility reflects registered configuration and camera selection, rather than a successful hardware connection.

The package summary adds the draft frontend adapter `deliveries.totals({ date, timeZone })`, returning the echoed calendar date/time zone plus `receivedToday` and `receivedAllTime`. The mock aggregates the entire authenticated location, independently of list pagination or photo/tracking availability. The live adapter returns 501; an endpoint and server aggregation are not implemented. Agree the authoritative reporting time zone, day boundary, history/duplicate-scan policy, and permissions. The current UI uses the device's local calendar day and refreshes at midnight/resume; it never treats a loaded page as the all-time total.

Package search extends the draft frontend adapter to `deliveries.list(cursor?, { search? })`. The explicit mock matches resi and courier name/code across the authenticated location **before** cursor pagination. It applies Unicode NFKC normalization, case-insensitive literal terms, and whitespace splitting; every term must match, with a 200-character input limit. Summary totals stay unfiltered. Agree the backend search parameters, matching rules, pagination stability and authorization before implementing a live adapter. This change adds no backend endpoint, database index, or firmware dependency; live search returns the existing 501 integration-unavailable error without fetching a guessed route.

## Legacy API compatibility

| Existing operation                                                                          | Supported semantics                             | Frontend boundary                                                                                         |
| ------------------------------------------------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/shipments?limit=100`                                                           | Shipment snapshots with offset pagination       | Preserved in `lib/api.ts`; cannot infer household, scan timestamp, distinct delivery event, or CCTV photo |
| `POST /api/v1/shipments`                                                                    | Manual courier/resi registration                | Legacy utility client only; not signup or the primary household journey                                   |
| `POST /api/v1/shipments/:id/refresh`                                                        | Explicit tracking refresh                       | Not a delivery detail GET                                                                                 |
| `GET /api/v1/notifications`                                                                 | Database feed with `shipment_id`                | Not remote push, installation association, or an agreed delivery-ID payload                               |
| `POST /api/v1/detections`, `/detections/frame`                                              | Optional shared-key ingest and barcode decoding | Firmware/backend transport, not authenticated user or household-device identity                           |
| Draft auth, `/deliveries`, photos, devices, members, setup and push installation operations | Not supplied by these legacy endpoints          | Typed service interfaces with explicit mocks or unavailable live state; no guessed live endpoints         |

Keep one configured base URL, without duplicating a version prefix. Preserve snake-case legacy wire DTOs (`types/api.ts`) separately from household view models (`types/app.ts`). Prefix differences alone do not require backend rewrites.

## Current scaffold mismatches observed in source

These are source-level findings, not end-to-end verification results.

| Evidence                                                                                                                                                                                                                                                                                                 | Mismatch and effect                                                                                                                                                                                                                                                                                               |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`services/shipments.py`](../../apps/backend/src/cekrir/services/shipments.py) calls `provider.lookup(...)` before `repository.register(...)`; [`main.py`](../../apps/backend/src/cekrir/main.py) maps `TrackingUnavailable` to HTTP 502.                                                                | When tracking fails for a new scan, the shipment/event and notification row are not persisted. The confirmed behavior requires saving the scanned resi and continuing notification with tracking unavailable. Existing duplicate lookup is handled before provider lookup, but new arrivals are blocked.          |
| [`repository.py`](../../apps/backend/src/cekrir/repository.py) persists shipments and a database notification row, and deduplicates by the database uniqueness on courier/resi. `/api/v1/notifications` lists those rows; no push sender or token-installation API appears in `apps/backend/src/cekrir`. | This is not household-scoped delivery history or push fanout. No evidence here establishes short-window per-household dedupe, stable frontend delivery DTOs, or notification dispatch to household installations.                                                                                                 |
| [`main.cpp`](../../apps/esp32/src/main.cpp) submits a camera frame on a timer (`kScanIntervalMs` defaults to 3 seconds in [`config.example.h`](../../apps/esp32/include/config.example.h)); it parses `detected_count` from the HTTP response and changes retry/cooldown timing.                         | This is periodic frame polling, not the confirmed proximity-triggered scan flow. The firmware source contains no proximity sensor input or scan-success light/buzzer feedback. The response is parsed, but it does not drive the required courier acknowledgement. Physical hardware behavior remains unverified. |
| [`dependencies.py`](../../apps/backend/src/cekrir/api/dependencies.py) checks a shared ingestion key only when one is configured; [`routes.py`](../../apps/backend/src/cekrir/api/routes.py) exposes shipment and notification listing without household user auth.                                      | This cannot authorize household users or protect cross-household delivery/photo reads. The mobile app must wait for authenticated household contracts; the device ingestion key is not a user session.                                                                                                            |
| [`camera.py`](../../apps/backend/src/cekrir/api/camera.py), [`routes.py`](../../apps/backend/src/cekrir/api/routes.py), and [`repository.py`](../../apps/backend/src/cekrir/repository.py) contain no BARDI capture or protected photo-content operation.                                                | A selected-camera photo association, authorized JPEG response, independent photo state, and frontend object URL lifecycle still need an agreed integration.                                                                                                                                                       |
| [`schemas.py`](../../apps/backend/src/cekrir/schemas.py) uses UUID shipment IDs and the legacy shipment DTO; the frontend proposal treats IDs as opaque and defines household delivery/detail types.                                                                                                     | The frontend adapter needs an agreed mapping to real backend IDs and DTOs. Do not force the draft model or `/v1` names onto the backend without owner review.                                                                                                                                                     |
| [`tracking.py`](../../apps/backend/src/cekrir/services/tracking.py) defaults to a demo provider; its HTTP provider calls a generic normalized gateway.                                                                                                                                                   | The demo provider does not make a live courier request. The real provider, SPX access, contract, credentials, and response validation remain unresolved.                                                                                                                                                          |

The frame endpoint returns an ingestion acknowledgement containing a detection count and shipment identifiers. The firmware parses the count and changes its retry/cooldown interval. The needed product acknowledgement is specifically successful decode feedback to the courier; no light/buzzer response path is present in the inspected firmware.

That HTTP acknowledgement currently waits for shipment registration, which waits for tracking lookup. Separate accepted-decode feedback from enrichment so the courier does not wait for CCTV, tracking, or push. Persist the event and notify despite enrichment failure. Capture the selected BARDI camera for delivery context; an ESP32 label image is not a substitute. Bound proximity-triggered attempts, stop on success/timeout/removal, and require removal before rearming; no idle barcode-image uploads. The exact sensor, wiring, retry/session limits, and feedback patterns remain open. The PRD's five-minute household/resi deduplication window is a tunable working default rather than a performance guarantee.
